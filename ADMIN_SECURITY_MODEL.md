# STAR HOME — Admin Security Model

Статус: **модель угроз и правила проверок для Phase A–F.**

## 1. Границы доверия

```
[Браузер]  — недоверенный
   │  cookie star_home_session = base64(userId, membershipId, sv, exp).HMAC(session secret)
   ▼
[Next :3456]  — доверенный транспорт, не принимает решений о правах
   │  { method, input, session, client } подписано HMAC(internal secret)
   ▼
[API :3457]  — единственный writer и единственное место решений
   │
   ▼
[Stores → Postgres]
```

| Что | Откуда | Доверие |
| --- | --- | --- |
| `session.userId`, `session.membershipId`, `session.sv` | подписанная cookie → подписанный payload | Подлинность — да. Актуальность проверяется по store на каждом запросе |
| `role`, `companyId`, scope, permissions | **только store**, по `membershipId` | Вычисляются в API |
| `input.*` (objectId, unitId, userId, membershipId, role, scope) | браузер | **Никогда.** Только как «что хочу тронуть», всегда сверяется со scope |
| `client.ip`, `client.device` | заголовки запроса в Next | Для аудита. Не для решений о правах |

## 2. Правила

1. **Deny by default.** RPC без записи в `methodPolicy` отклоняется.
2. **Одна точка решения.** `decide.can(actor, permission, target)`. Доменные функции не проверяют роли сами.
3. **Actor строится заново на каждом запросе**: user `ACTIVE`, `sv` совпадает с `sessionVersion`, membership существует, `ACTIVE`, не истекла.
4. **Target из input резолвится на сервере**: `unitId` → unit → object → company. Проверяется, что цепочка лежит внутри scope actor.
5. **Чужая компания → 404**, своя компания вне scope → **403**, нет сессии → **401**.
6. **Поля, которые нельзя передать с клиента**: `userId` автора, `companyId`, `role` actor, `permissions`, `createdBy`, `result` аудита. Если такое поле пришло в input, оно игнорируется.
7. **Назначение ролей** подчиняется правилам ранга и вложенности scope (`ADMIN_PERMISSION_MATRIX.md`, раздел 4). Проверяет API.
8. **Изменение прав действует сразу.** Роль, scope, блок, переопределение матрицы → `sessionVersion++` у затронутых пользователей.
9. **Ответ содержит только данные scope.** Фильтрация в UI не считается защитой.
10. **Маски полей.** Логин, телефон, email жителя видны начиная с MANAGER.
11. **Подтверждённость.** Ворота, инженерия, банк: «успех» только при подтверждении адаптера. Иначе результат `ERROR` в аудите и честное сообщение.

## 3. Сессии

| Сейчас | Станет |
| --- | --- |
| Cookie 14 дней, отзыва нет | + `sv`. Несовпадение с `User.sessionVersion` → 401, cookie удаляется |
| Блокировки нет | `User.status = BLOCKED` → вход 403 «Доступ приостановлен», активные сессии отклоняются |
| `lastLoginAt` нет | пишется при успешном входе |

Старые cookie без `sv` принимаются как `sv = 1`, чтобы текущие сессии не слетели при деплое.

## 4. CSRF и происхождение запроса

- Cookie `httpOnly`, `sameSite=lax`, `secure` в production. Уже так.
- Мутации только `POST/PUT/PATCH/DELETE` с JSON-телом.
- Добавить в `proxy.ts` проверку `Origin` / `Sec-Fetch-Site` для `/api/*` с мутирующими методами: чужой origin → 403.

## 5. IP и устройство

Next route handler читает `x-forwarded-for` (первое значение, только если перед Next стоит доверенный прокси; иначе адрес сокета) и `user-agent`. Агент сокращается до «Safari · iOS» / «Chrome · macOS». В подписанный payload они уходят как `client`.

Server components без запроса пользователя передают `client = null`. Для них в аудите «—».

## 6. Аудит

Пишется **всегда**, в том числе при отказе:

| Категория | Действия |
| --- | --- |
| RBAC | добавление сотрудника, изменение роли, изменение scope, блок, восстановление, удаление, изменение матрицы |
| ACCESS | открытие ворот и точек, создание и отзыв пропуска |
| SECURITY | вызов охраны, обработка тревоги, запрос кадра камеры |
| ENGINEERING | команды устройствам, изменение уставок, смена статуса работы устройства |
| FINANCE | оплата, счета, возвраты, экспорт |
| DATA | удаление объекта, корпуса, единицы, жителя |
| SETTINGS | настройки объекта и режимов жизни, компании |
| AUTH | вход, отказ во входе заблокированному, отклонённая сессия |
| SERVICE | смена статуса заявки |

Отказ по правам (`DENIED`) пишется для методов с `!` в матрице. Для просмотра отказы не пишутся, чтобы журнал не зашумлялся.

Свойства журнала:

- только добавление, метода изменения и удаления нет;
- пароли, коды пропусков и токены в записи не попадают;
- `changes` хранит значения, а не секреты;
- просмотр ограничен scope и категориями (SECURITY видит только ACCESS и SECURITY).

## 7. Угрозы и ответы

| Угроза | Ответ |
| --- | --- |
| Подмена `objectId` в запросе на чужой объект | Target резолвится на сервере, 403/404, DENIED в аудите |
| Подмена `role` / `permissions` в теле | Поля игнорируются, actor из store |
| Прямой вызов API без UI | Та же проверка: UI не участвует в решении |
| Повышение себе роли через Team | Запрет на изменение себя + правило ранга |
| Выдача scope шире своего | Проверка вложенности scope |
| Блокировка последнего CA | 409 с объяснением |
| Заблокированный продолжает работать | `sessionVersion` + проверка status на каждом запросе |
| Утечка между объектами через общие списки | Каждый список фильтруется по scope на сервере (P1) |
| Подбор пароля | Существующий Redis-лимит 8 попыток / 10 минут |
| Запись мимо API | Удаление мёртвых хелперов, которые пишут в store из Next (P10) |
| Раскрытие чужой компании по коду ответа | 404 вместо 403 |
| Подделка «успеха» устройства | Успех только по подтверждению адаптера |

## 8. Security QA (Phase F)

Автотесты (`node:test` через `tsx`, stores привязаны к памяти через `bindStore`, живой Postgres не трогается):

1. Матрица: для каждой роли × каждого RPC-метода — ожидаемый код 200 / 403 / 404.
2. Scope: OBJECT_ADMIN объекта A вызывает методы с `objectId` объекта B → 403. С объектом другой компании → 404.
3. Подмена: в input передаются `role: "SUPER_ADMIN"`, `companyId`, `userId`. Результат не меняется.
4. Сессия: блок пользователя → следующий запрос 401. Смена роли → старая cookie 401.
5. Team: назначение роли выше своей, scope шире своего, изменение себя, блок последнего CA — отказ.
6. Аудит: каждое критическое действие даёт ровно одну запись с верными `actorRole`, `objectId`, `result`.
7. Ответы: списки `ops*`, `residents`, `team`, `audit` не содержат записей вне scope.

Ручная проверка на живом API: `curl` с подписанным payload для каждой роли демо-аккаунтов, прямой вызов с чужим `objectId`.

## 9. Открытые вопросы

1. Редактируемая матрица (переопределения компании) в Phase C — или только просмотр системной матрицы.
2. SECURITY в этом этапе работает в урезанной Admin Console, а отдельная Security Console делается позже — или нужна сейчас.
3. Демо-сотрудники в живой базе (аддитивно, без reseed): OBJECT_ADMIN, MANAGER, SECURITY, SERVICE_OPERATOR, ACCOUNTANT для «Сияния». Нужны для визуальной и security-проверки ролей.
4. «Удалить» в Команде — отзыв membership с сохранением User для журнала (рекомендуется) или полное удаление.
