# STAR HOME — Multi-tenancy

Одна платформа, много компаний, много объектов. Данные компании и объекта не пересекаются.

## 1. Модель изоляции

Общая база PostgreSQL. Изоляция логическая, на каждом запросе.

Обязательный владелец:

- почти каждая строка имеет `companyId`;
- всё, что относится к территории, дополнительно имеет `objectId`;
- единица недвижимости имеет `unitId`, и через неё объект и компанию.

Отдельная база на посёлок не создаётся. Отдельный backend на объект не создаётся.

## 2. Цепочка проверки

```
AUTHENTICATION
  → COMPANY ACCESS
    → OBJECT ACCESS
      → RESOURCE ACCESS
        → ACTION PERMISSION
```

Источник актёра — серверная сессия.

Нельзя доверять присланным:

- `userId`
- `role`
- `companyId`
- `objectId`

Идентификатор в URL означает «какой ресурс просят», не «имеет ли право». Право вычисляет API.

## 3. Membership

Право — это запись, а не поле на пользователе.

```
Membership
  userId
  companyId
  role
  objectId    nullable
  unitId      nullable
  expiresAt   nullable, обязательно для GUEST
  status
```

Примеры:

| Кто | Membership |
| --- | --- |
| Житель одного дома | company + object + unit + RESIDENT |
| Житель двух объектов | две записи RESIDENT |
| Администратор компании | company + COMPANY_ADMIN, без unit |
| Администратор объекта | company + object + OBJECT_ADMIN |
| Гость | company + object + unit + GUEST + expiresAt |

После логина API возвращает доступные membership. Клиент не выбирает посёлок, если запись одна.

## 4. Правила запросов

Каждый репозиторий принимает контекст:

```
actorId
companyId
objectId? 
allowedActions
```

Запрос списка домов:

```
WHERE companyId = context.companyId
  AND objectId = context.objectId
```

Запрос по id добавляет те же условия. Чужой id возвращает «не найдено», без чужих полей.

`SUPER_ADMIN` — единственная роль платформы. Она явно отмечена в сессии и всё равно пишет audit. Обычные роли компанию из сессии не расширяют.

## 5. Что видит интерфейс

Житель видит свои единицы и общие для его объекта сведения, которые разрешены роли: статус дома, свои гости, свои счета, свои заявки.

Житель объекта A не получает объекты, гостей, счета, камеры и заявки объекта B.

Администратор компании видит объекты своей компании. Переключатель объекта фильтрует рабочий стол. Фильтр на сервере, не только в сайдбаре.

## 6. AI и устройства

AI получает тот же контекст membership. Инструмент не принимает произвольный `objectId` от модели: идентификатор подставляет policy из сессии.

Прямой SQL, прямой доступ к базе и прямой доступ к устройству для AI запрещены.

Адаптер устройства исполняет команду только если API уже проверил action permission и, для опасного действия, подтверждение.

## 7. Аудит

Запись:

- actor
- companyId
- objectId
- action, например `OPEN_GATE`
- target
- result: SUCCESS или ERROR
- error
- timestamp

Критическое событие охраны: push жителю, уведомление охраны, запись в audit. Это требование следующих фаз, не Phase 1.
